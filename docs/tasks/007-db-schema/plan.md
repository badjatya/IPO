## Goal and scope

- **In scope:**
  - The full [db.md](../db.md) schema as a Drizzle schema in TypeScript: the 12 enums, all 23 tables with each column, type, nullability, default, key and index exactly as db.md lists them, the `watched_symbols` view, and the `citext` extension for `users.email` — which gets its type through a drizzle `customType`, because drizzle has no built-in citext column.
  - Versioned SQL migrations checked into `web/db/migrations/`: the tables migration is **generated** by drizzle-kit and never hand-edited; the `citext` extension, the decided `settings` seed rows and (if needed) the view live in separate **custom migrations** (`drizzle-kit generate --custom`), ordered so the extension runs before the tables and the seed after them. `analysis_daily_limit_platform` is deliberately **not** seeded (decided 2026-10-29: D08 is open, no number may be invented).
  - `web/lib/db.ts` wraps the existing neon-http client with Drizzle — one connection, not a second one.
  - A Neon-branch test harness, `npm run test:db`: creates an empty, short-lived, schema-only branch per run from `NEON_API_KEY`/`NEON_PROJECT_ID` (H06), applies the migrations over the branch's unpooled URL, runs the rule and schema tests over the pooled URL, and deletes the branch in a `finally`.
  - Tests for the constraints that carry rules (one open job per stock, unique `dedupe_key`, unique `exchange_ref`), plus a full-schema catalog check (tables, enums, view, partial unique indexes, composite FKs), the seed rows and the watchlist cascade delete.
  - A schema-drift check in the existing `web` CI job and a new `db` job; the docs this touches (db.md, tech.md, arch.md, ai.md) updated with their status labels.
- **Out of scope:** the auth library's own tables (010), the import script (008), code that reads `settings` (013/018/022), the platform cap's default value (D08), any change to `analysis/`, `reports/`, `data/`, or to the agent.

## Approach

- **The schema is written once, in TypeScript; the migration SQL is the artifact that builds an empty branch.** `web/db/schema.ts` mirrors db.md exactly — money as `numeric(12,2)`/`numeric(14,2)` (percentages `numeric(7,2)`, `pe`/`times` `numeric(10,2)`), times `timestamptz` and dates `date` (db.md principles 5–6). Defaults appear only where db.md lists them (`anchor_done false`, `positives`/`red_flags`/`notes` `{}`, `users.role 'user'`, `analysis_requests.charged true`). For the insert columns db.md leaves blank — the time columns (`created_at`, `queued_at`, `requested_at`, `recorded_at`, `added_at`, `at`, `updated_at`) — the schema uses `default now()`; the two bare `uuid` keys (`users.id`, `analysis_jobs.id`) use `default gen_random_uuid()` (core Postgres 13+, no extension). This is a schema detail, not an Open decision; the db.md update records it. drizzle-kit generates the tables migration into `web/db/migrations/`; re-running `generate` must be a no-op, so the checked-in SQL is stable — a CI step enforces it. If a later task changes the schema, it adds a new migration, never edits a generated file.
- **Generated files are never hand-edited.** drizzle-kit never emits `CREATE EXTENSION`, so the `citext` extension, the seed rows and (if needed) the view each get their own custom migration (`drizzle-kit generate --custom`), created in an order that makes the journal run them where they belong: the extension first (before the tables use it), the tables migration next, the seed after. `users.email` gets its `citext` type through a drizzle `customType` in `schema.ts`.
- **One connection.** `web/lib/db.ts` keeps the lazy neon-http client on the pooled `DATABASE_URL` and gains a `db()` wrapper (Drizzle over that same client) — ADR-0025's "rather than adding a second connection". drizzle.config.ts pins `DATABASE_URL_UNPOOLED` and `driver: "pg"` for drizzle-kit, because migrations can't run through the pooler.
- **Seeding rides along with the schema build.** The three decided settings rows (`ask_daily_limit_per_user = 5`, `analysis_monthly_limit_per_user = 3`, `analysis_refresh_after_days = 30`, values the human already settled, with the db.md descriptions for the admin page, `updated_at = now()`, `updated_by = NULL`) live in a custom migration after the tables, so an empty branch is complete after `migrate`. `analysis_daily_limit_platform` gets **no row at all** — decided 2026-10-29: it stays unseeded until D08 sets a number; no invented default (AGENTS.md rule 6). Absence is legal by design (one row per key), and the decided behaviour is **gate closed**: while the row is missing, no new or refreshed analysis is dispatched — the dispatch rule reads the cap's row and requires it to exist; jobs stay queued and the loading screen uses the existing "platform cap → job waits" experience (arch § 7.2). No Gemini quota is spent under an unset cap; the per-user monthly limit stays the only gate that opens. Tasks 018/022 build this.
- **The rule-carrying constraints are tested on a real, disposable, empty Neon branch.** `web/scripts/neon-branch.mjs` creates a branch through the Neon API (`NEON_API_KEY`, `NEON_PROJECT_ID` — H06) from the project's default branch with `init_source: "schema-only"` and `expires_at` set to now + 1 day, drops the `public` and `drizzle` schemas (then recreates `public`) so the migrations demonstrably build the full schema from nothing, runs `npx drizzle-kit migrate` over the branch's unpooled URI, runs the db tests (a separate Vitest config, `node` environment) over the pooled URI, and deletes exactly the branch it created in a `finally` — refusing to run if that branch is the project's default branch or `dev`. This is what db.md's "tests run against real Postgres, not a mock" means, and it is the planned exception to "no live calls" — the tests touch only our own Neon project, gated behind CI secrets.
- **The plain `npm test` can never run the db tests, by config.** The offline `vitest.config.mts` excludes `tests/db/**` (keeping Vitest's default excludes); the db tests run only under `vitest.db.config.mts`, whose setup file **throws** unless the harness set the marker `NEON_TEST_BRANCH_ID` (naming the branch it created). The harness sets `DATABASE_URL` and the marker only in its child processes' environment, so a laptop `npm test` — or a stray `vitest run tests/db` — can never touch the `dev` branch that a stale `DATABASE_URL` points at.
- **The constraints and the full schema are asserted specifically.** The rule tests assert SQLSTATE `23505` *and* the index name the error message names (read from `pg_catalog`, so the check survives drizzle's naming); the open-job test covers `running` + `queued` (must fail) and a second `queued` after `done` (must pass). A separate shape test reads `pg_catalog`/`information_schema` for the 23 tables, the 12 enums with their values, the `watched_symbols` view, the partial unique indexes and the unique `exchange_ref`/`dedupe_key` indexes, and the composite FKs. The offline `schema.test.ts` (module exports) is kept as a cheap extra.
- **Docs flip Decided → Running** where the schema now exists, migrations are checked in, and the branch-per-test-run flow actually runs.

## Risks and rollback

- **drizzle-kit vs TypeScript 7** (the app ships `typescript ^7.0.2`). drizzle-kit loads its own config; if the installed version chokes on the project's setup, pin the version the human installed, or as a last resort author the migration SQL by hand from db.md as a custom migration — `drizzle-kit migrate` still applies it and the SQL is what CI verifies (a hand-written migration is a last-resort *replacement*, never an edit to a generated file).
- **Custom-migration ordering and view support.** The citext custom migration is created before the tables migration so the journal runs it first; `watched_symbols` is generated by `pgView` or gets its own custom migration. If the installed drizzle-kit's journal ordering ever proves uncontrollable, the harness executes the extension SQL itself (over the branch's unpooled URI) before `drizzle-kit migrate` — same effect, still no hand-edited generated file. Any substitute is noted under "Changes during build".
- **`drizzle-kit migrate`'s driver.** The plan installs `pg` as a devDependency and pins `driver: "pg"` in `drizzle.config.ts`. If the installed drizzle-kit still refuses to migrate (some versions want `postgres` instead), the fallback is to run the migrations from the harness with drizzle-orm's own migrator over `drizzle-orm/neon-serverless` (WebSocket — `ws` already ships with `@neondatabase/serverless`), using the same migration files, still over the unpooled URL. Recorded under "Changes during build" if used.
- **Neon free tier and API.** Each `db` job creates and deletes one branch, with `expires_at` set to now + 1 day at creation (the 7-day TTL in `web/neon.ts` applies only to branches created with `neon checkout`, not raw API branches, so it is not a backstop here). Cost per run is a branch plus a few queries — negligible against 100 compute-hours. If the create-branch response omits connection URIs, the script builds them from the branch's endpoint/database/role objects. `push` and `pull_request` both trigger CI, so a PR run creates two branches — harmless with the expiry set. Fork PRs don't get the secrets; that's fine, task branches are in-repo.
- **Schema-only branch availability.** If the installed Neon API version doesn't support `init_source: "schema-only"`, the harness creates a normal branch and still drops `public`/`drizzle` (then recreates `public`) before migrating: the migrations still build the schema from an empty database, and the only cost is a brief copy of the parent's data onto a throwaway branch deleted in the same run.
- **Wrong connection for migrations.** Running drizzle-kit over the pooled URL breaks session state under PgBouncer; the config pins `DATABASE_URL_UNPOOLED` and the `db` job fails loudly, never silently — the fix is a branch edit, not a data repair.
- **The offline/test rule tension.** "Tests run against a Neon branch" is this task's planned exception to "no live calls": the db tests address only our own Neon project via CI secrets, they are excluded from `npm test` by config, and their own config refuses to start without `NEON_TEST_BRANCH_ID` — a local `npm test` can never reach `dev`, even when a stale `DATABASE_URL` points at it.
- **The unset cap (decided).** Gate closed: analyses of never-analysed stocks wait until an admin sets the cap; the loading screen explains why (018/022 build that UX).
- **D04 may reshape `users`.** db.md already says the final shape follows the auth library; if 010's library uses a different id type or email handling, 010 adds a migration to adjust — not a blocker here.
- **Rollback.** Nothing depends on the schema yet (008 unbuilt), so a bad migration is fixed by editing it on the branch and re-running; after merge, a revert restores the old state (the migrations folder is the only addition). The dev branch (H01) holds only the seed rows; it can be recreated with `neon checkout dev` if ever needed. No data-loss path exists.

## Changes during build

1. **`driver: "pg"` omitted from `drizzle.config.ts`.** The installed drizzle-kit (0.31.11) validates `driver` against `d1-http | expo | aws-data-api | pglite | durable-sqlite`; `driver: "pg"` fails. The review's note predicted this. drizzle-kit uses the installed `pg` automatically for a plain Postgres URL, so nothing else changes: migrations still run over `DATABASE_URL_UNPOOLED` via drizzle-kit's `migrate` command.
2. **`watched_symbols` needed no custom migration.** `pgView` generated `CREATE VIEW "public"."watched_symbols" AS (select distinct "watchlist_items"."symbol" from "watchlist_items")` inside the tables migration, so the plan's "or its own custom migration" branch was never taken. The custom migrations are exactly two: `0000` (citext extension, created before the tables migration so it runs first) and `0002` (the three settled settings seed rows; no cap row).
3. **CI drift step scoped from the `web` working directory.** The step runs `npx drizzle-kit generate && test -z "$(git status --porcelain db)"` (the `web` job's `defaults.run.working-directory` is `web`, so the pathspec `db` covers `web/db`). `git status --porcelain` catches both modified and untracked files (a new migration), which a plain `git diff` would miss. Verified locally: with the schema untouched the output is empty and `generate` is a no-op; with a probe column added, `generate` created an untracked `0003_*.sql` and the command would fail.
4. **`imports.started_at` / `finished_at` are nullable.** db.md listed no Null flag for them; the build reads that as nullable (a failed import may lack `finished_at`). Recorded in db.md's `imports` table.
5. **Bare `numeric` columns pinned to the plan's widths.** db.md wrote `numeric` without precision for `ipo_outcomes.pe`/`size_cr` and `stock_quotes.price`/`change_pct`/`market_cap_cr`/`pe`. The build applies the plan's mapping (money `numeric(12,2)`, ₹ crore `numeric(14,2)`, percentages `numeric(7,2)`, `pe`/times `numeric(10,2)`); db.md's tables now show the exact types.
6. **The offline Vitest config spells out Vitest's default excludes.** Setting `exclude` replaces Vitest's defaults, so `vitest.config.mts` lists the documented default pattern set plus `tests/db/**` — the plan's "keeping Vitest's default excludes" holds in effect, and the db tests are additionally impossible to run accidentally (separate config, marker guard in `tests/db/setup.ts`).
7. **Code-review round 1, finding 1: 0001 regenerated, not patched.** The composite keys were declared as `.primaryKey()` on each column, so drizzle-kit emitted one `PRIMARY KEY` clause per column and Postgres rejects the table. The fix declares each composite key once via `primaryKey({ columns: [...] })` in the table's extra config (the column-level `.references()` stay). Because nothing has ever applied the migrations (test:db has never run), I regenerated `0001` instead of adding a follow-up migration — a follow-up could never run, since the broken 0001 fails before the journal advances: removed the stale `0001` and seed artifacts, ran `drizzle-kit generate` (new `0001_cute_exodus.sql` with `CONSTRAINT "…_pk" PRIMARY KEY(…)` table constraints), recreated the seed custom migration as `0002_outstanding_lyja.sql` (identical content). `generate` is a no-op afterwards, so the drift check stays green.
8. **Code-review round 1, findings 2, 4, 5: host, arch row, naming.** The harness's API host was `https://neon.tech/api/v2`, which 308-redirects to `neon.com` (404) and drops the `Authorization` header on the redirect — now `https://console.neon.tech/api/v2`. `docs/arch.md`'s Database row now keeps both statuses (test branches **Running**, preview branches **Decided** with D11). `WORKTREE_ROOT` renamed to `WEB_ROOT` (it points at `web/`), and `?connection_uris=true` dropped from the create-branch call (the API returns `connection_uris` whenever it creates an endpoint).
9. **Code-review round 1, finding 3: primary-key shape test.** `web/tests/db/schema-shape.test.ts` gained a test reading `pg_constraint` (`contype = 'p'`) with `pg_get_constraintdef`: exactly one PK row per table and db.md's columns for each — composite for the seven natural-key tables, single-column for the rest, `id` for the identity/uuid tables.
10. **Code-review round 2, finding 6: default-branch lookup.** The first real CI `db` run exposed that the Neon API v2 Branch object marks the default branch with `default: true` — there is no `is_default` field, so `branches.find((branch) => branch.is_default === true)` never matched and the harness died before creating a branch. The lookup is now the pure, offline-tested helper `findDefaultBranch(branches)` matching `branch.default === true` (fixture in the API's documented shape, including a test that the old `is_default` spelling does *not* match), and the "no default branch found" error now lists every branch it saw (`name [default: …]`) so the next field mismatch shows up in the job log. The create-response fields the harness reads next — `branch.id`, `connection_uris[].connection_uri`, `endpoints[].host`, `roles[].name`/`.password` — were checked against the API v2 reference and all match its documented shapes (the fallback's extra reads degrade to the correct `neondb` default). No branch was created by the failed run, so nothing needed cleaning up.
11. **Code-review round 3, finding 7: unwrap drizzle's error wrapper.** drizzle-orm 0.45 wraps every driver error in `DrizzleQueryError` (message `Failed query: …`, the Postgres error on `.cause` — `pg-core/session.js`), so the rule tests saw `code`/`constraint`/`message` as `undefined`. `captureViolation` (in `web/tests/db/schema-rules.test.ts`) now **fails the test when the statement succeeds** — a dropped index can no longer read as the generic "undefined was not 23505" — then returns `error.cause ?? error` (the `NeonDbError` with `code`/`constraint`/`message`). The four unique-violation tests assert `code === "23505"` and that the error's `constraint` field or its `message` names the index read from the catalog (via the shared `expectUniqueViolation`). The new helper asserts from inside a helper, so `web/.oxlintrc.json`'s `vitest/expect-expect` now lists `expectUniqueViolation` in `assertFunctionNames` (keeping the vitest defaults `expect`, `expectTypeOf`, `assert`, `assertType`).
12. **Code-review round 3, finding 8: queued-after-done probe.** The "allows a new queued job once the previous one is done" test selected all rows for the symbol and trusted the first back as `queued` — the insert had succeeded, but `done` came back first. It now selects every status for the symbol and asserts the sorted set is `['done', 'queued']`, so the test proves both the new queued row and the old done row without depending on row order.
13. **Code-review round 3, finding 9: partial-index assertions on parts, not on the definition text.** `pg_get_indexdef` does not echo the migration text: it schema-qualifies the table (`ON public.analysis_jobs`), rewrites `in ('queued', 'running')` to `= ANY (ARRAY['queued'::job_status, 'running'::job_status])` and wraps predicates in parens (`WHERE (symbol IS NOT NULL)`), so the three `includes(...)` strings could never match. The shape test now reads each partial unique index's table, definition and `pg_get_expr(ix.indpred, ix.indrelid)` and asserts the pieces: the indexed column (`using btree (…)` in the definition) and the predicate's column/value tokens case-insensitively — plus the exact set of the three partial unique indexes (`analysis_jobs`, `ipos`, `stocks`).
14. **Code-review round 3, finding 10: composite-FK regex.** `pg_get_constraintdef` writes `REFERENCES ipo_snapshots(ipo_key, taken_at)` with no space before the `(`, so the regexes' `ipo_snapshots \(` never matched. Both regexes now allow `\s*` before `\(`.
15. **Code-review round 3, finding 11: enum values as `text[]`.** `e.enumlabel` has type `name`, so `array_agg` returned `name[]`, which the serverless driver can't parse (the values arrived as raw text and the deep-equal failed — the twelve keys were there on both sides). The query now aggregates `e.enumlabel::text`, so the driver returns a JS array of strings.
