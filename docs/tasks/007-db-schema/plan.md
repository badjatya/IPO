## Goal and scope

  - A `db` job in CI; the docs this touches (db.md, tech.md, arch.md, ai.md) updated with their status labels.
- **Out of scope:** the auth library's own tables (010), the import script (008), code that reads `settings` (013/018/022), the platform cap's default value (D08), any change to `analysis/`, `reports/`, `data/`, or to the agent.

## Approach

- **The schema is written once, in TypeScript; the migration SQL is the artifact that builds an empty branch.** `web/db/schema.ts` mirrors db.md exactly — money as `numeric(12,2)`/`numeric(14,2)` (percentages `numeric(7,2)`, `pe`/`times` `numeric(10,2)`), times `timestamptz` and dates `date` (db.md principles 5–6), defaults only where db.md lists them (`anchor_done false`, `positives`/`red_flags`/`notes` `{}`, `users.role 'user'`, `analysis_requests.charged true`). drizzle-kit generates `web/db/migrations/0000_*.sql`, which CI applies to an empty branch; re-running `generate` must be a no-op, so the checked-in SQL is stable. If a later task changes the schema, it adds a new migration, never edits 0000.
- **One connection.** `web/lib/db.ts` keeps the lazy neon-http client on the pooled `DATABASE_URL` and gains a `db()` wrapper (Drizzle over that same client) — ADR-0025's "rather than adding a second connection". drizzle.config.ts pins `DATABASE_URL_UNPOOLED` for drizzle-kit, because migrations can't run through the pooler.
- **Seeding rides along with the schema build.** The three decided settings rows (`ask_daily_limit_per_user = 5`, `analysis_monthly_limit_per_user = 3`, `analysis_refresh_after_days = 30`, values the human already settled, with descriptions for the admin page) are appended to the initial migration, so an empty branch is complete after `migrate`. `analysis_daily_limit_platform` gets **no row at all** until D08 decides a number — no invented default (AGENTS.md rule 6). The `settings` table is one row per key, so absence is legal by design; db.md records how the app treats it ([Decisions needed](#decisions-needed)).
- **The rule-carrying constraints are tested on a real, disposable Neon branch.** `web/scripts/neon-branch.mjs` creates a branch through the Neon API (`NEON_API_KEY`, `NEON_PROJECT_ID` — H06), runs `npx drizzle-kit migrate` with the branch's unpooled URI, runs the rule tests (Vitest, per-file node environment) with the pooled URI, and deletes the branch in a `finally`; `web/neon.ts`'s 7-day TTL is the backstop if a delete fails. This is what db.md's "tests run against real Postgres, not a mock" means, and it is the planned exception to "no live calls" — the tests touch only our own Neon project, gated behind CI secrets. The plain `npm test` stays offline: the rule-test files skip cleanly when `DATABASE_URL` is absent, and nothing in the offline suite ever creates a branch.
- **The three named constraints are the tests' target** (the partial unique index on `analysis_jobs`, `alerts.dedupe_key`, `announcements.exchange_ref`), because those indexes *are* the rules; the view, the seed rows and the `watchlist_items` cascade are tested as the cheap adjacent guarantees.
- **Docs flip Decided → Running** where the schema now exists, migrations are checked in, and the branch-per-test-run flow actually runs.

## Risks and rollback

- **drizzle-kit vs TypeScript 7** (the app ships `typescript ^7.0.2`). drizzle-kit loads its own config; if the installed version chokes on the project's setup, pin the version the human installed, or as a last resort write the migration SQL by hand from db.md — `drizzle-kit migrate` still applies it and the SQL is what CI verifies.
- **drizzle-kit view support.** If the installed version can't generate `watched_symbols`, append the `CREATE VIEW` to the initial migration (same treatment as the seed) and note it under "Changes during build".
- **Neon free tier and API.** Each `db` job creates and deletes one branch; the 7-day TTL in `web/neon.ts` is the backstop if a delete fails. Cost per run is a branch plus a few queries — negligible against 100 compute-hours. If the create-branch response omits connection URIs, the script builds them from the branch's endpoint/database/role objects. Fork PRs don't get the secrets; that's fine, task branches are in-repo.
- **Wrong connection for migrations.** Running drizzle-kit over the pooled URL breaks session state under PgBouncer; the config pins `DATABASE_URL_UNPOOLED` and the `db` job fails loudly, never silently — the fix is a branch edit, not a data repair.
- **The offline/test rule tension.** "Tests run against a Neon branch" is this task's planned exception to "no live calls": the db tests address only our own Neon project via CI secrets, and the offline suite skips them without `DATABASE_URL` — `npm test` on a laptop or in the `web` CI job never creates a branch.
- **The unset cap.** If the human picks gate-closed, analyses of never-analysed stocks wait until the cap is set in admin; the loading screen explains why (018/022 build that UX).
- **D04 may reshape `users`.** db.md already says the final shape follows the auth library; if 010's library uses a different id type or email handling, 010 adds a migration to adjust — not a blocker here.
- **Rollback.** Nothing depends on the schema yet (008 unbuilt), so a bad migration is fixed by editing it on the branch and re-running; after merge, a revert restores the old state (the migrations folder is the only addition). The dev branch (H01) holds only the seed rows; it can be recreated with `neon checkout dev` if ever needed. No data-loss path exists.
