## Goal and scope

- **In scope:**
  - A pure, standard-library module `stock_worker/alerts.py` with the six alert rules — `pledge_up`, `promoter_down`, `fii_move`, `dii_move`, `results`, `announcement` — as deterministic functions over the record shapes the 014 fetchers already produce (plain dicts keyed by the `db.md` column names). No database, no AI, no network.
  - Each rule returns an **alert record** keyed exactly as the `db.md` `alerts` columns: `kind`, `severity`, `title`, `detail` (always `None` here; Gemini fills it in 020), `dedupe_key`, `source_table`, `source_id`. Titles and every number in them come from Python, from stated fields only; a missing value renders as "not available", never an estimate ([AGENTS.md](../../AGENTS.md) rule 1).
  - A `compute_alerts(symbol, fetched, stored, existing_keys=(), thresholds=...)` orchestrator: takes the just-fetched records (`fetched`) **and** the records already on hand (`stored`) for each of the four series (`results`, `shareholding`, `pledges`, `announcements`), dedupes by natural key keeping the latest, joins pledge records to shareholding quarters on `quarter_end`, and raises an alert **only for a record that is new against `stored`** — a change rule compares the new quarter with the latest quarter on record before it (which may come from `stored`), so a stock's first run (nothing stored) raises no alerts at all. It also skips any alert whose `dedupe_key` is already in a caller-supplied set (`existing_keys`), so the same input never raises the same alert twice. Deterministic output order.
  - Thresholds and severities per **D10**, settled by the human at round-1 plan review ([plan-review.md § Decisions](plan-review.md)): `pledge_up` rise ≥ 1.00 pp, `promoter_down` fall ≥ 2.00 pp, `fii_move`/`dii_move` absolute move ≥ 1.00 pp; `results` → `info`, `announcement`/`fii_move`/`dii_move` → `watch`, `pledge_up`/`promoter_down` → `warning`. They live in code — `DEFAULT_THRESHOLDS` and the `SEVERITIES` map in `stock_worker/alerts.py`, still passable as parameters (`thresholds=`) — with no `settings` rows.
  - Tests (`tests/test_stock_alerts.py`) for every rule: first sight on a stock (empty `stored` → no alerts at all), first quarter on record (no alert), missing data (no alert), threshold boundary, exact titles, dedupe keys (the `db.md` example `HDFCBANK:pledge_up:2026-09-30`), `source_table`/`source_id` forms, idempotence (same input twice → same output; `existing_keys` → nothing re-emitted), and an integration test that runs the 014 parsers over the saved `tests/fixtures/nse_stock/` fixtures end to end. No live sites, no AI APIs.
  - Doc updates: `db.md`, `data-sources.md`, `arch.md`, `tech.md`, `ai.md`, and a new ADR-0027 (status **Proposed**) recording D10 as the human settled it at round-1 review. Roadmap changes for `main` are listed under "Doc updates", including the **new task 027** settled at review for XBRL parsing (FII/DII).
- **Out of scope:**
  - Writing any database row, migration, seed or `settings` row — the `alerts` table's schema is built in 007 and its rows are written by the worker in 018. No Postgres driver.
  - Writing `data/stocks/<SYMBOL>/…` files — that is 018's persistence.
  - XBRL/PDF fetching and parsing. `fii_pct`/`dii_pct` stay missing (014 returns `None`), the `fii_move`/`dii_move` rules stay silent until task 027 (settled at round-1 review) feeds real values; 016's rules are forward-compatible, exactly as `shareholding.py` is.
  - Rating announcement importance (`importance`) and writing `alerts.detail` — those are Gemini's jobs in 020, with their `ai_*` provenance there. 016's `announcement` rule consumes the `importance` value, and 016 writes no `ai_*` column.
  - Name→symbol resolution for pledge rows (which carry only `comName`; that is 015/018's job) and the quote/consolidated-results gaps (018's records).
  - Anything in `web/`, any GitHub Actions workflow, any new package or dependency. Standard library only, like 014.

## Approach

### 1. One pure module, `stock_worker/alerts.py`

The rules are stateless, standard-library functions in the package 014 created. They consume the same record shapes the 014 parsers return (keyed by the `db.md` column names, `Decimal`/`None` values) and emit alert records keyed by the `db.md` `alerts` columns, so 018 can insert them straight into the `alerts` table. No module reads the database, a file, a setting or the network; nothing here is wired into any workflow yet, exactly like 014's fetchers were when they shipped.

Alert record contract (keys = `alerts` columns):

| Key | Value |
| --- | --- |
| `kind` | one of `pledge_up`, `promoter_down`, `fii_move`, `dii_move`, `results`, `announcement` |
| `severity` | from the code-held severity map (D10) |
| `title` | built by Python from stated fields — the `db.md` example style: "Promoter pledge up from 4% to 11%" |
| `detail` | `None` — Gemini's explanation is written in 020 against the same alert |
| `dedupe_key` | `<SYMBOL>:<kind>:<period>` where the period is the triggering quarter's `period_end`/`quarter_end`, or `<SYMBOL>:announcement:<exchange_ref>` — uppercase symbol, the `db.md` example form |
| `source_table` / `source_id` | `shareholding`/quarter_end for the four shareholder rules, `quarterly_results`/period_end for `results`, `announcements`/exchange_ref for `announcement` |

Formatting helpers (`format_pct` for percentages with trailing zeros stripped, `format_cr` for ₹ crore with commas and up to 2 dp) are tested alongside the rules; `None` renders as "not available", never a guessed number.

### 2. Change rules: shareholding, pledges, FII/DII

`pledge_up`, `promoter_down`, `fii_move` and `dii_move` each take `(symbol, prev_record, curr_record, threshold_pp)` and compare the **new quarter** with the **latest quarter on record before it** (sorted ascending by `quarter_end`; an omitted quarter simply means the next one on record is the comparison partner — the comparison is "vs the previous quarter on record"). For `promoter_down`, `fii_move` and `dii_move` the records are shareholding records; for `pledge_up` they are pledge records — the orchestrator supplies both after joining on `quarter_end` (Approach § 4), because 014's `shareholding.parse` does not carry `promoter_pledged_pct` (only `pledges.parse` does, in separate records). A record pair that is missing the compared field on either side yields no alert — including a quarter that has shareholding but no pledge row (`pledge_up` stays silent).

Settled thresholds, in percentage points, compared as `Decimal`s; a move of exactly the threshold fires ("at least" semantics), less does not: `pledge_up` rise ≥ 1.00 pp, `promoter_down` fall ≥ 2.00 pp, `fii_move`/`dii_move` absolute move ≥ 1.00 pp. Titles state the exact before and after values ("Promoter pledge up from 4% to 11%", "Promoter holding down from 52.1% to 48.9%", "FII holding up from 14.2% to 16.1%"). The `fii_move`/`dii_move` rules are identical logic over `fii_pct`/`dii_pct`; today those are always `None` on real data, so they stay silent until task 027 feeds parsed values — "missing data (no alert)" is their steady state, and the tests pin it.

A new quarter with no earlier quarter on record has no pair, so no change alert fires — the quarter that starts a symbol's record is the baseline, not an event. This is the roadmap's "first quarter on record (no alert)", tested through `compute_alerts`.

### 3. Existence rules: new results, important announcements

- **`results`**: fires **only for a new results record** (its `period_end` not in `stored`) that has an **earlier quarter on record** — an earlier quarter from `stored`, or an earlier-new fetched quarter. A fresh stock's history backfill (nothing stored) stays quiet, because the whole fetched history becomes the baseline; from the second run on, each new filing alerts once, ever. The title states the period and the revenue and PAT the filing states — "Quarterly results for 2026-09-30: revenue ₹12,826 cr, PAT ₹872 cr", with "not available" for fields the record does not state. Dedupe key `RELIANCE:results:2026-09-30`. The rules only ever compare within one consolidation series: the input records have `consolidated` always `False` today, and the plan's contract says the caller (018) passes a single-consolidation series — consolidated figures are never compared with standalone, per the data-sources gap note.
- **`announcement`**: fires **only for a new announcement** (its `exchange_ref` not in `stored`) whose `importance` is `high` or `medium` — the value Gemini writes in 020 (until then `importance` is `None`, so no announcement alert fires; the missing-data test pins it). An announcement already on record never re-alerts, even when 020 sets its importance afterwards — 016's rule fires only for announcements new in the fetched set; 020 writes `importance` and the explanations. The title is the announcement's own title as NSE stated it (data, quoted as-is; announcements carry no numbers). Dedupe key `RELIANCE:announcement:<exchange_ref>`, the exchange's own unique ID; an announcement without `exchange_ref` cannot be keyed and alerts nothing.

### 4. "Only what's new", "the same input never raises the same alert twice"

Four layers, the first three in this task:

0. **Only records new against `stored` alert.** `compute_alerts(symbol, fetched, stored, ...)` receives each of the four series twice: `fetched` (the records 018 is about to persist for this run) and `stored` (the records already in the database for the symbol). A record is *new* when its natural key — `period_end` (results), `quarter_end` (shareholding and pledges), `exchange_ref` (announcements) — is not in the `stored` set, and only new records can produce an alert. A revised filing whose natural key is already in `stored` is not new and never re-alerts (its values still serve as `prev` for later new quarters). For a stock with nothing stored, the whole fetched history is the baseline and raises **no alerts at all** — the first-sight case, pinned in a test. The same history split across runs alerts only from the second run on, and then only the quarters that run introduced; the old "backfill burst" risk disappears.
1. **Deterministic rules**: identical input yields identical alert records — same `dedupe_key`, same title, same order. A test runs `compute_alerts` twice on the same input and asserts the lists are equal and the keys unique.
2. **`existing_keys`**: `compute_alerts(..., existing_keys=...)` drops any alert whose `dedupe_key` is already there (018 passes the symbol's stored alert keys as a second guard). A test passes the first call's keys to the second call and asserts nothing new comes back.
3. **The unique index on `alerts.dedupe_key`** (built by 007) plus insert-on-conflict in 018 is the final guard — outside this task, noted in the contract.

**The quarter timeline.** To apply the change rules, `compute_alerts` builds one timeline per symbol: the union of `stored` and `fetched` shareholding and pledge records, deduped by `quarter_end` (a fetched record supersedes a stored record with the same key) and sorted ascending. Each entry holds its shareholding record and its pledge record for that quarter; either may be absent. For every **new** quarter `Q`:
- `promoter_down`, `fii_move`, `dii_move`: `curr` is `Q`'s shareholding record, `prev` the latest earlier entry that has a shareholding record.
- `pledge_up`: `curr` is `Q`'s pledge record, `prev` the latest earlier entry that has a pledge record — a quarter with shareholding but no pledge row is simply not a `pledge_up` candidate, and a quarter with a pledge but no shareholding is not a `promoter_down`/FII/DII candidate.

**Dedupe per series.** Each input set is deduped by natural key, keeping the latest record: `filed_at` for results and shareholding, `disclosed_at` for pledges, `announced_at` for announcements. A `None` timestamp sorts *older* than any stated timestamp (a record that states no filing time cannot be proven newer). When timestamps are equal, or `None` on both sides, the winner is the record that is greater under a canonical serialisation (key-sorted, `Decimal`s via `str()`), so the result never depends on input order. Tests pin: two records for the same quarter with different `filed_at` keep the later one; equal/`None` timestamps keep the same winner in either input order; a revision (natural key already in `stored`) never re-alerts.

### 5. D10 and the FII/DII scoping: settled at round-1 review

The human settled D10 at the round-1 plan review ([plan-review.md § Decisions](plan-review.md)); the values below are written in where the plan previously carried a recommendation.

| Rule | Threshold (pp, quarter-on-quarter, "at least X fires") | Severity |
| --- | --- | --- |
| `pledge_up` | rise ≥ 1.00 | `warning` |
| `promoter_down` | fall ≥ 2.00 | `warning` |
| `fii_move` | absolute move ≥ 1.00 | `watch` |
| `dii_move` | absolute move ≥ 1.00 | `watch` |
| `results` | — | `info` |
| `announcement` | — | `watch` |

The thresholds and severities live in **code**: `DEFAULT_THRESHOLDS` and the `SEVERITIES` map in `stock_worker/alerts.py`, still passable as parameters (`thresholds=`), with **no `settings` rows** — they are analytic parameters, not user-facing quotas or caps (rule 6, confirmed by the reviewer's note). ADR-0027 (status **Proposed**) records the four decisions; it also states that `promoter_pledged_pct` is a **share of the promoter's holding** (not of total equity), so 020's explanation can state it correctly.

FII/DII: the human settled a **separate task 027** ("XBRL shareholding parsing") to do the parsing. 016 ships `fii_move`/`dii_move` forward-compatible, tested on synthetic records; until 027 feeds real `fii_pct`/`dii_pct`, the rules stay silent on real data ("missing data, no alert").

### 6. What 018 consumes

018 imports `compute_alerts` and calls it per symbol with:
- `fetched=` — the records it is about to persist this run: results, shareholding, pledges (already resolved to the symbol by the 015 name→symbol map; 016 never sees `company`) and announcements;
- `stored=` — the records already in the database for the symbol, in the same parsed shapes; 016 needs the full stored records for results, shareholding and pledges (the change rules and `has_earlier` compare against stored values), while for announcements the `exchange_ref`s suffice (newness is the only announcement check);
- `existing_keys=` — the symbol's stored alert keys (second guard).

Both sets use the **014 parsed record shapes** — shareholding records without `promoter_pledged_pct`, separate pledge records (`quarter_end`, `promoter_pledged_pct`, `disclosed_at`) — so 016 never sees a DB row. 018 reconstructs the stored shapes from its read: a stored `shareholding` row that has `promoter_pledged_pct` becomes one shareholding record plus one pledge record. 016 itself does the `quarter_end` join between shareholding and pledge records (Approach § 4), so 018 does no merging before calling. 018 inserts the returned alert records with `dedupe_key` as the conflict target against the unique index (007). The contract to watch in 018: an **incomplete `stored` set** makes old quarters look new, so a partial history read would burst stale alerts — 018 must pass everything it has (and its own tests will pin it).

| --- | --- | --- |
| 018 passes an incomplete `stored` set | Stored history looks new, so a stock's first real run bursts alerts for every historical quarter | The contract in § 6 requires 018 to pass everything it has and to reconstruct the stored shapes from its own read; 018's tests pin it. | A stock's history backfill wants to raise no alerts | The first run after 015 fetches a full history; without the stored/fetched split it would alert every historical crossing back to 2022 | By design with the split: nothing stored (first sight) makes the whole fetched history the baseline — zero alerts, pinned in tests (Approach § 4). | Thresholds set in D10 need tuning later | Alerts too noisy or too quiet | One-line change to `DEFAULT_THRESHOLDS` in code (the settled home) — the rule code is identical, no migration; alert rows already written are untouched |
