> Invite-only accounts with Better Auth ([ADR-0028](../adr/0028-better-auth-invite-only.md)): email and password sign-in, sessions in Postgres through the Drizzle adapter, and `users.role`. **No public sign-up.** An admin invites a user by email, and the user gets a one-time link, sent through Resend, to set their password. Users can reset a forgotten password by an emailed link. Includes a way to make the first admin, an admin-only invite form (a minimal one; the settings page is 013), route guards, rate limits on sign-in and reset requests, CSRF protection, and every user query scoped to the signed-in user.
>

## Goal and scope

- **In scope:**
  - Better Auth wired into the existing Next.js app: `better-auth` + `resend` packages (installed by the human), the server config over the existing Drizzle `db()` connection (`web/lib/db.ts`, task 007), the client, and the Next.js handler on `/api/auth/[...all]`. Sessions live in Postgres through the Drizzle adapter ([ADR-0028](adr/0028-better-auth-invite-only.md)).
  - The schema change: Better Auth's `session`, `account`, `verification` tables, the `rate_limit` table for database-backed rate limiting, and the extra `users` columns it needs (`email_verified`, `image`, `updated_at`), as a generated drizzle-kit migration. `users` keeps its db.md columns (`uuid` id with `gen_random_uuid()` default, `citext` email unique, `role` text defaulting to `user`); Better Auth's user model is mapped onto them. All auth-table ids are `uuid` because Better Auth is told to generate uuids (`advanced.database.generateId: "uuid"`), so the `uuid` columns hold what it writes.

  - The first-admin mechanism (settled at plan review: a CLI script; must not be a public route), tests (unit + the Neon-branch suite from 007), and the doc updates that mark accounts Running.

## Approach

- **Better Auth is the whole accounts engine; the app adds a thin shell (pages, one API route, a script, guards).** `web/lib/auth.ts` builds the server instance with `drizzleAdapter(db(), { provider: "pg" })` over the single existing Drizzle connection (ADR-0025: one connection), `emailAndPassword` with `disableSignUp: true` and `revokeSessionsOnPasswordReset: true` (a reset ends every live session — recovering a compromised account also kicks any attacker's session out; round 2 item 5), the `sendResetPassword` hook routed to the mail module, `baseURL` from a new `AUTH_URL` env var (default `http://localhost:3000`), `emailAndPassword.resetPasswordTokenExpiresIn: 60 * 60 * 24` — seconds, the type 1.7.14 expects (settled: one mechanism, one expiry of 24 hours, for both invite and reset; round 2 item 2), `user.additionalFields: { role: { type: "string", input: false } }` mapped onto the existing `users.role` text column, `rateLimit` with database storage and custom rules, and `advanced.database.generateId: "uuid"` so the ids Better Auth generates fit the `uuid` columns. **No admin plugin** (review item 1, option b): the plugin would drag in `banned`, `banReason`, `banExpires` and `impersonatedBy` columns and admin powers the app doesn't use — the app's only admin concept is `users.role = "admin"`, enforced by the server-side guard. No `advanced.csrfCheck`: the origin check is the library default against `baseURL`/`trustedOrigins`, on and never disabled. `AUTH_SECRET` is required in production (missing → fail fast at server start); outside production a dev fallback is allowed for local and test runs, never a real value (review item 5). A missing `RESEND_API_KEY` or `EMAIL_FROM` fails the same way in production — at server start, like the secret (round 2 item 4). The client is `web/lib/auth-client.ts` (`authClient` only — no `adminClient`); the handler is `toNextJsHandler(auth)` on `/api/auth/[...all]`. Exact option names are confirmed against the installed version's types during the build (see Risks).
- **Schema: one generated migration, `users` untouched in its existing columns.** The Drizzle adapter throws when a model field is missing from its table, so the tables carry the exact 1.7.14 fields (Context read), in the repo's snake_case convention: `session` (unique `token`, `user_id` uuid FK → `users.id` cascade, `expires_at`, `ip_address`, `user_agent`, `created_at`/`updated_at`), `account` (unique `(provider_id, account_id)`, `user_id` uuid FK cascade, the credential `password` hash lives here — never in `users` — plus the OAuth-token fields `access_token`, `refresh_token`, `id_token`, `access_token_expires_at`, `refresh_token_expires_at`, `scope`), `verification` (`identifier`, `value`, `expires_at`), and `rate_limit` (`key` unique, `count`, `last_request` **bigint** — 1.7.14 stores the last request as milliseconds since the epoch (`Date.now()`), not a timestamp; round 2 item 1) for the database rate-limit store. Every auth table's id is `uuid` with `defaultRandom()` (consistent with the repo's "bare uuid keys" convention), matching the `generateId: "uuid"` ids Better Auth writes, and every `user_id` FK is `uuid` to match `users.id`; db.md's `users.id uuid` stays (review item 2). `users` gains only `email_verified` (boolean, default false), `image` (text) and `updated_at` (timestamptz, default now()) — `id`/`email`/`role`/`name`/`created_at` stay exactly as they are, and `role` is read and written through the `additionalFields` mapping above. `npx drizzle-kit generate` produces the migration; re-running it stays a no-op (the CI drift check proves it). db.md's "auth tables built by task 010" line flips to Running, and gains the `rate_limit` table.
- **One email path, for two kinds of account email.** `web/lib/mail.ts` exports `sendAccountEmail({ to, subject, text, html })` and `assertMailConfig()` (throws when `RESEND_API_KEY` or `EMAIL_FROM` is missing). **Because the hook fires without awaiting, a send-time throw would only reach the log after the invite route already answered "Invite sent" — so mail config is checked up front: the invite route calls `assertMailConfig()` before creating any row and answers 500 with a plain "email is not configured" if it fails, and in production `web/lib/auth.ts` fails at server start without the mail config, the same as `AUTH_SECRET`** (round 2 item 4). Print mode never runs in production (review item 5). With the key set, it sends through Resend's SDK; without it *and outside production*, it prints the rendered email to the console (dev mode; local runs and the Neon harness). Tests replace the module entirely (`vi.mock`). The only callers are the `sendResetPassword` hook paths — there is no other email code path, so ADR-0028's "no alert digests, no other email" is structural, not just convention. **The hook chooses the wording** (review item 8): a user with no credential `account` row yet gets the invite wording ("set up your account"), anyone with one gets the reset wording — the invited user's email is an invite, the forgot-password email is a reset, and a never-set-up invitee who asks for a reset still gets invite wording. Both wordings carry only the product placeholder name ([ADR-0028](adr/0028-better-auth-invite-only.md)), the one-time link, and the ADR-0012 disclaimer line. Never research content. **The hook does not await delivery** (review item 10): it fires the email and logs failures (via `advanced.backgroundTasks` / `waitUntil` if the installed version supports it, else a `.catch` on the fired promise), so the public forgot-password response never waits on Resend — a slow delivery must not reveal that an address exists. Trade-off, stated: a delivery failure isn't shown to the person who asked, and for this form that's acceptable; failures land in the server log. The invite route reports the same generic success either way, so its response stays uniform for known and unknown addresses (review item 7).
- **Invite, forgot-password and set-password are one token mechanism.** The link a user receives is Better Auth's reset-password link (`<redirectTo>?token=…`), with one expiry, 24 hours, for both flows (settled: decision 2; re-inviting voids the old link). Invite flow: the admin submits the minimal form → `/api/admin/invite` (guarded: proxy cookie check, then in the route an explicit same-origin check and `requireAdmin`) validates the email, looks it up (citext); if the address is new it creates the user with role `user` and no password through a **scoped Drizzle insert** (`db().insert(users).values({ email, name?, role: "user" })`, id and timestamps from DB defaults — no admin plugin, no client-set role possible), if it already exists it changes nothing about the row (no new row, role never touched — an invite neither demotes an admin nor promotes a user; review item 7); either way it voids outstanding links for that user (`delete from verification where identifier like 'reset-password:%' and value = <user id>` — reset rows are keyed by token, not by address; review item 7), then calls `auth.api.requestPasswordReset({ body: { email } })`, whose hook sends the email (invite wording for a user with no credential account). The response is identical whether the address existed or not. Forgot-password calls the same reset API; the page always answers with the same "If an account exists for this email, a link is on its way" — no email goes to an unknown address, and the test asserts both halves. The invitee opens `/reset-password?token=…`, types a password, Better Auth verifies the token (single-use: the row is deleted on success; expired rows are refused), and signs in on `/sign-in`. Sign-out is a button on the admin invite page calling `authClient.signOut()`.
- **First admin: a CLI script, never a route** (settled: decision 1). `web/scripts/first-admin.mjs` is plain JavaScript — it cannot import the TypeScript `web/lib/auth.ts` (no `tsx` in the project), so it does **only the database part**: it takes an email (and optional name) from argv, connects through the existing neon-http client with `DATABASE_URL` from the environment, and upserts that user to role `admin` (insert on missing, `update … set role='admin'` on existing — idempotent; re-running promotes and never duplicates). It writes no `verification` row and no token — Better Auth stays in charge of tokens (review item 6). It prints the outcome and tells the human to set the password through the running app's `/forgot-password`, where the link prints in dev (print mode) and emails once H07 is done. The passwordless admin row is harmless: nothing can sign in with it until a password is set, but the app can issue the reset link the moment it runs.
- **Guards are layered; the proxy is not the only check.** Next 16.4's middleware replacement is `web/proxy.ts` and runs on Node (review item 9): it is a fast cookie check on `/admin/*` and `/api/admin/*` — no session cookie → redirect `/sign-in` (pages) or 401 JSON (API). The authoritative checks live server-side: `web/app/admin/layout.tsx` calls a session-and-role helper (`auth.api.getSession` with `headers()`) and redirects or 403s, exactly as the invite route calls `requireAdmin` — middleware bypasses have happened before (CVE-2025-29927), so pages and routes never trust the proxy alone. The invite route re-checks even where the layout already did (defense in depth).
- **Rate limits and CSRF are config plus tests.** `rateLimit: { enabled: true, storage: "database", customRules: { "/sign-in/email": { window: 900, max: 10 }, "/request-password-reset": { window: 3600, max: 5 } } }` — the rules are an **object keyed by path**, not an array, per 1.7.14 (round 2 item 3) — `enabled: true` because 1.7.14 switches the limiter off unless `NODE_ENV === "production"`, and `storage: "database"` because the default in-memory store is per instance on any serverless host (review item 4). Limits are keyed by client IP and path, not by email address. `/api/admin/invite` is not behind the library limiter and server-side `auth.api.*` calls skip it, so the earlier "invite 5/hour" claim is dropped — admin-only, plus the role and origin checks, is the gate (review item 4). CSRF: Better Auth's origin check covers `/api/auth/*` by default (against `baseURL`/`trustedOrigins`; never `disableCSRFCheck`); **the app's own cookie-authenticated routes are not covered, so `/api/admin/invite` adds an explicit check — `Origin` must equal the `AUTH_URL` origin, else 403 — and 013's settings route must do the same** (review item 3). The limits are code constants: security parameters, not product quotas (AGENTS.md rule 6 covers quotas such as Ask and analysis limits, which stay in `settings`).
- **Tests.** Offline Vitest (jsdom, `vi.mock` of `@/lib/auth-client` and `@/lib/mail`, no network, no database, no live sites): mail module print/Resend modes **and the production-throw branch** (stubbed `NODE_ENV`, missing key → throws; same for the auth secret resolution, review item 5); hook wording — invite vs reset — with the credential-account lookup mocked (review item 8); forms render and submit the right calls; the always-same forgot-password message; invite-route logic with mocked auth (valid invite calls `requestPasswordReset` and the mail carries invite wording; non-admin 403; unauthenticated 401; malformed email 400 and no mail; **cross-origin invite POST with a valid admin session → 403**, review item 3; **mail config missing → 500 "email is not configured", no row created, no mail**, round 2 item 4); guard helper and proxy predicates with mocked sessions (review item 9); first-admin pure helpers (argv parsing, upsert SQL). The existing-address invite behaviour needs a real database — it lives in `tests/db/auth.test.ts`, not the mocked unit tests (review item 7). Neon-branch integration (`npm run test:db`, the task-007 harness, CI's `db` job): after migrate, the four auth tables and the new `users` columns exist; end-to-end invite → email captured → set password with the token → token fails on second use → sign in → session shows role `user`; expired token refused; re-invite voids the old link and the fresh one works; invite to an existing address → no new row, old links voided, role unchanged, identical response; the first-admin script → forgot-password → set password → session shows role `admin`; a password reset revokes pre-reset sessions (round 2 item 5); the user's call to the invite API refused while the admin's succeeds; each session token resolves only to its own user (scoping); sign-up refused; N failed sign-ins (through the HTTP handler, so the limiter runs — the harness has no client IP, so this exercises the single shared bucket, review item 4) → the next is refused; forged-Origin sign-in refused (library check) and cross-origin invite refused (route check). Synthetic addresses only (`…@example.com`), `AUTH_SECRET` generated per run inside the harness, mail in print mode in the child environment — tests never touch Resend, and no real user data lands anywhere in git.
- **Docs flip the labels:** db.md, tech.md and arch.md mark accounts Running; tech.md gains the `AUTH_URL` variable (both the config table and `web/.env.example`, kept in step by the env-example test) and flips Resend and the app's accounts to Running; ADR-0029 (first-admin bootstrap) records the mechanism the human settled at plan review, so it is **Accepted**, not Proposed.

## Risks and rollback

- **Better Auth version specifics (option names, adapter mapping).** The plan names the config keys and the exact table columns from Better Auth 1.7.14 (reviewed against the published package in plan review round 1). The build still confirms every option against the installed package's types and the drizzle adapter's expectations before relying on it. Differences (e.g. the `sendResetPassword` hook's context shape, whether `advanced.backgroundTasks` exists, the rate-limit model's exact field names) are handled in the build and recorded under "Changes during build". If the installed version misbehaves, the human can pin an exact version — no fallback design change needed.
- **H07 is not done (Resend account and verified domain).** Tests and the Neon-branch suite never need it (mail module replaced / print mode), and the first-admin script doesn't either. A *real* invite is a manual check after merge and needs `RESEND_API_KEY` + `EMAIL_FROM` (H07); until the domain is verified, Resend's test sender delivers only to the account owner's address. In production mail config is checked up front, never discovered at send time: the invite route calls `assertMailConfig()` before creating any row and answers 500 "email is not configured" when it's missing, and `web/lib/auth.ts` fails at server start without it — the admin always sees a missing config, and a live one-time token is never printed to a log (review item 5; round 2 item 4). Outside production the app runs with print-mode mail.
- **Fire-and-forget mail delivery (review item 10).** The reset hook doesn't await delivery, so a delivery failure is logged, not shown to the requester — for the forgot-password form that's deliberate (awaiting a slow Resend call would reveal that an address exists); for the invite route the response is the same "Invite sent" either way. If `advanced.backgroundTasks`/`waitUntil` is unsupported on the installed version, the fired promise with `.catch(log)` is the fallback; on a serverless host that could drop an in-flight email, which is a known, logged, acceptable phase-1 loss.
- **Guards depend on the layered design, not the proxy** (review item 9). `web/proxy.ts` runs on Node in Next 16.4 and is only a fast cookie check; the authoritative session-and-role checks live in the admin layout and the invite route, so a middleware bypass (CVE-2025-29927 class) doesn't expose the admin surface. No edge-runtime concern: the proxy and the helpers all run on Node.
- **Rate limiting before a host is chosen (D11 open).** The `rateLimit` store is in the database (not per-instance memory), but limits are keyed by client IP and path; until `advanced.ipAddress` is configured for the chosen host (025), every request lands in one shared bucket and Better Auth logs a warning. Acceptable for phase 1; the step-8 rate-limit test deliberately exercises that shared bucket because the test harness has no client IP (review item 4). Revisited by the security review (024) and the host task (025).
- **First admin before any deploy.** The script only creates/promotes the row; the password is set through the running app's `/forgot-password`, so the admin can't sign in until the app is up. That's fine after deploy; locally it means running the app once and using the printed link.
- **No user data in git.** Test fixtures use `example.com` addresses only; the first-admin script prints to the terminal; `web/.env.example` and `docs/` hold variable names, never values (the env-example test enforces emptiness). The privacy note for the submission must mention emails going to Resend (ADR-0028) — not this task's change, but flagged.
- **Local runs touch `dev`.** `neon checkout dev` sets `DATABASE_URL` to the dev branch; signing in during local development writes users/sessions there. That is the intended environment (H01); a misrun first-admin script is repaired by re-running it (idempotent) or a one-line SQL `update users set role='user' where email=…`. No research data is ever at risk — auth tables are app tables.
- **Rollback.** Nothing beyond 010 depends on accounts yet (013 builds later). Reverting the merge removes the pages, routes, script and the guard; the four auth tables and the `users` columns are dropped by a follow-up migration if ever needed (a new migration, never an edit to the checked-in one). Since sessions and passwords exist only in the database, a revert loses no git-owned data.
