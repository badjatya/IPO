> Invite-only accounts with Better Auth ([ADR-0028](../adr/0028-better-auth-invite-only.md)): email and password sign-in, sessions in Postgres through the Drizzle adapter, and `users.role`. **No public sign-up.** An admin invites a user by email, and the user gets a one-time link, sent through Resend, to set their password. Includes a way to make the first admin, an admin-only invite form (a minimal one; the settings page is 013), route guards, rate limits on sign-in and reset requests, CSRF protection, and every user query scoped to the signed-in user.

## Approach

- **Better Auth is the whole accounts engine; the app adds a thin shell (pages, one API route, a script, guards).** `web/lib/auth.ts` builds the server instance with `drizzleAdapter(db(), { provider: "pg" })` over the single existing Drizzle connection (ADR-0025: one connection), `emailAndPassword` with `disableSignUp: true` and the `sendResetPassword` hook routed to a small mail module, the `admin` plugin with `adminRoles: ["admin"]` and `defaultRole: "user"` (our `users.role` text column is what it reads), `baseURL` from a new `AUTH_URL` env var (default `http://localhost:3000`), `secret` from `AUTH_SECRET` (dev fallback for local/test runs, never a real value), `rateLimit` and `advanced.csrfCheck`. The client is `web/lib/auth-client.ts` (`authClient` + `adminClient`); the handler is `toNextJsHandler(auth)` on `/api/auth/[...all]`. Exact option names are confirmed against the installed version's types during the build (see Risks).
- **Schema: one generated migration, `users` untouched in its existing columns.** `web/db/schema.ts` gains `session` (unique `token`, FK → `users`, `expires_at`), `account` (unique `(provider_id, account_id)`, FK → `users`, the credential `password` hash lives here — never in `users`), and `verification` (`identifier`, `value`, `expires_at`) with Better Auth's Drizzle-adapter fields in the repo's snake_case convention. `users` gains `email_verified` (boolean, default false), `image` (text) and `updated_at` (timestamptz, default now()) — db.md's `id`/`email`/`role`/`name`/`created_at` stay exactly as they are. The user model maps the id as DB-managed (`input: false`), so `gen_random_uuid()` keeps producing uuids and `citext` email stays unique. `npx drizzle-kit generate` produces the migration; re-running it stays a no-op (the CI drift check proves it). db.md's "auth tables built by task 010" line flips to Running.
- **One email path, three uses.** `web/lib/mail.ts` exports `sendAccountEmail({ to, subject, text, html })`: with `RESEND_API_KEY` set it sends through Resend's SDK; without it, it prints the rendered email to the console (dev mode). Tests replace the module entirely (`vi.mock`); `print` mode serves the first-admin script. The only caller is Better Auth's `sendResetPassword` hook — there is no other email code path, so ADR-0028's "no alert digests, no other email" is structural, not just convention. Email body: product placeholder name ([ADR-0028](adr/0028-better-auth-invite-only.md)), the one-time link, and the ADR-0012 disclaimer line. Never research content.
- **Invite, forgot-password and set-password are one token mechanism.** The link a user receives is Better Auth's reset-password link (`<redirectTo>?token=…`). The invite flow: admin submits the minimal form → `/api/admin/invite` (guarded twice: middleware, then a `requireAdmin` helper inside the route) validates the email, creates the user with role `user` and no password (admin-plugin `createUser`; if the installed version insists on a password for server calls, fall back to a direct insert through `db()` — recorded under "Changes during build"), deletes any prior verification rows for that address (re-invite voids the old link), then calls `requestPasswordReset`, whose hook sends the invite. Forgot-password calls the same reset API; the page always answers with the same "If an account exists for this email, a link is on its way" — no email goes to an unknown address, and the test asserts both halves. The invited user (or the admin, on first bootstrap) opens `/reset-password?token=…`, types a password, Better Auth verifies the token (single-use: the row is deleted on success; expired rows are refused), and signs in on `/sign-in`. Sign-out is a button on the admin invite page calling `authClient.signOut()`.
- **First admin: a CLI script, never a route.** `web/scripts/first-admin.mjs` takes an email argument and runs with `DATABASE_URL` set: it upserts the user with role `admin` (id left to the DB default), forces the mail module's print mode, requests a reset token, and prints the set-password URL to the terminal. Idempotent: re-running prints a fresh link without duplicating rows; running it on an existing user promotes that user. This proposal is under "Decisions needed" for the human to confirm.
- **Guards.** The Next 16 middleware location (`web/middleware.ts` or its renamed replacement in the installed version) protects `/admin/*` and `/api/admin/*`: no session → redirect to `/sign-in` (pages) or 401 JSON (API); a session whose `role` is not `admin` → 403. `auth.api.getSession` with the request headers is edge-compatible (the neon-http driver is fetch-based). The invite route re-checks the role (defense in depth), so the route works even if middleware changes.
- **Rate limits and CSRF are config plus tests.** Better Auth's `rateLimit` (proposed values: sign-in 10 attempts / 15 minutes, reset and invite requests 5 / hour, per address) and `advanced.csrfCheck` (origin validated against `baseURL`). Whether the installed version stores attempts in memory or in the database is confirmed during the build; the limits are code constants, not `settings` rows — they are security parameters, not product quotas (AGENTS.md rule 6 covers quotas such as Ask and analysis limits, which stay in `settings`). The neon-branch tests assert both behaviours.
- **Tests.** Offline Vitest (jsdom, `vi.mock` of `@/lib/auth-client` and `@/lib/mail`, no network, no database, no live sites): mail module print/Resend modes, forms render and submit the right calls, the always-same forgot-password message, invite-route logic with mocked auth (admin ok, non-admin 403, unauthenticated 401, malformed email 400 and no mail, re-invite voids the old token), guard predicates with mocked sessions, first-admin helper functions. Neon-branch integration (`npm run test:db`, the task-007 harness, CI's `db` job): after migrate, the three auth tables and the new `users` columns exist; end-to-end invite → print-mode email → set password with the token → token fails on second use → sign in → session shows role `user`; expired token refused; the user's call to the invite API refused while the admin's succeeds; each session token resolves only to its own user (scoping); sign-up refused; N failed sign-ins refused for the rest of the window; forged-Origin sign-in refused. Synthetic addresses only (`…@example.com`), `AUTH_SECRET` generated per run inside the CI job, mail in print mode in the harness's child environment — tests never touch Resend, and no real user data lands anywhere in git.
- **Docs flip the labels:** db.md, tech.md and arch.md mark accounts Running; tech.md gains the `AUTH_URL` variable (both the config table and `web/.env.example`, kept in step by the env-example test) and flips Resend and the app's accounts to Running; a Proposed ADR records the first-admin mechanism once the human settles it.

## Decisions needed

1. **First-admin mechanism** (ADR-0028 and the roadmap leave it to the plan; it must not be a public route).
   - **Option A (recommended): a CLI script** — `web/scripts/first-admin.mjs` run by the human with `DATABASE_URL`: creates or promotes the user with role `admin`, reuses the app's own invite/reset path in print mode, prints the set-password URL to the terminal. No route, no server code changes, works before any deploy, idempotent.
   - Option B: an environment variable (`FIRST_ADMIN_EMAIL`) read at server start that bootstraps the account as a side effect of first boot. No route either, but it runs inside the app (two instances could race, and the account appears only once the server has started and the database is reachable).
   - Option C: a seed migration creating the account. Can't set a password and can't send or print a link — useless on its own; only a stepping stone to A or B.
   - Recommendation: **A**. It is the only option with no app-runtime behaviour, matches "a script run with the database URL" in ADR-0028, and the print-mode mail path is already the test seam.

2. **Invite-link and reset-link expiry** (ADR-0028: "Better Auth's reset-password token is the natural basis, with a longer expiry for invites").
   - Option A (recommended): one mechanism for both, Better Auth's own reset token, uniform `resetPasswordTokenExpiresIn` (24 hours), re-invite voids the old link. One code path, exactly the token Better Auth verifies and deletes on use — the "works once and expires" and "forgot password doesn't reveal" properties come from the library, not from custom code.
   - Option B: two expiries — forgot-password 1 hour, invite 7 days — with the invite stored as a separate custom `verification`-style row and a small custom set-password route for invites. Matches "longer for invites" literally, but forks the reset flow into two verifiers.
   - Recommendation: **A** (24 hours for both). A one-time link that lives a day is short enough for abuse and long enough for a human to act; re-invites void old links anyway. If the human prefers B, the build forks the invite path as described. The exact number is a code constant either way.

## Risks and rollback

- **Better Auth version specifics (option names, adapter mapping).** The plan names the config keys and the `id: { input: false }` mapping from Better Auth 1.7.x (the version in ADR-0028's evidence); the build confirms every option against the installed package's types and the drizzle adapter's expectations before relying on it. Differences (e.g. `rateLimit` storage being in-memory only, `createUser` requiring a password, or the verification row keyed by email rather than user id) are handled in the build and recorded under "Changes during build". If the installed version misbehaves, the human can pin an exact version — no fallback design change needed.
- **H07 is not done (Resend account and verified domain).** Tests and the Neon-branch suite never need it (mail module replaced / print mode), and the first-admin script doesn't either. A *real* invite is a manual check after merge and needs `RESEND_API_KEY` + `EMAIL_FROM` (H07); until the domain is verified, Resend's test sender delivers only to the account owner's address. In the meantime the app runs with print-mode mail (dev) — invites visibly fail loudly rather than silently if the key is missing.
- **Middleware and the edge runtime.** `auth.api.getSession` in middleware must run on the edge; the neon-http driver is fetch-based so this holds, but if the installed Better Auth pulls in a Node-only dependency there, the fallback is page/server-component guard checks plus the `requireAdmin` route helper (already in the plan for the invite API), recorded under "Changes during build".
- **Rate-limit storage on a multi-instance host (D11 open).** If the installed `rateLimit` store is per-process, limits apply per instance until the host is chosen (025) — acceptable for phase 1 and revisited by the security review (024). If a database-backed store is available, it is used.
- **No user data in git.** Test fixtures use `example.com` addresses only; the first-admin script prints the link to the terminal; `web/.env.example` and `docs/` hold variable names, never values (the env-example test enforces emptiness). The privacy note for the submission must mention emails going to Resend (ADR-0028) — not this task's change, but flagged.
- **Local runs touch `dev`.** `neon checkout dev` sets `DATABASE_URL` to the dev branch; signing in during local development writes users/sessions there. That is the intended environment (H01); a misrun first-admin script is repaired by re-running it (idempotent) or a one-line SQL `update users set role='user' where email=…`. No research data is ever at risk — auth tables are app tables.
- **Rollback.** Nothing beyond 010 depends on accounts yet (013 builds later). Reverting the merge removes the pages, routes, script and the guard; the three auth tables and the `users` columns are dropped by a follow-up migration if ever needed (a new migration, never an edit to the checked-in one). Since sessions and passwords exist only in the database, a revert loses no git-owned data.
