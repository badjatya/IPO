## Goal and scope

- **In scope:**
  - A Python package (location per D09: a new top-level `stock_worker/` package, standard-library only in 014) with one fetch + parse function per confirmed source: quote, quarterly results (standalone; consolidated handled as a recorded gap), results filings, announcements (per-symbol and market-wide), shareholding, pledges (per-symbol and market-wide).
  - All functions reuse `ipo_agent/net.py`'s `Client` (cookie jar, browser headers, gzip, retries) exactly as it is; nothing in the fetchers re-implements HTTP.
  - Each source returns **plain records** — dicts keyed exactly by the `db.md` column names (amounts already converted to the column's unit, ₹ crore, inside the parser; `decimal.Decimal` for amounts and percentages; `date`/`datetime` converted to ISO strings) that map 1:1 onto the `db.md` stock tables (`quarterly_results`, `shareholding`, `announcements`, `stock_quotes`). Fields that have no column (e.g. `period_start`, `audited`, pledge share counts, `isin`) stay in the record as extras, listed in the module docstring. Missing fields come back as `None`, never estimated; a stated `0` is a value, not a missing field. Records hold `Decimal`, which stdlib `json` cannot serialise, so the dev CLI prints them with `default=str`.
  - An orchestration function that primes the shared `Client` once per run (the `_primed` once-per-client pattern from `ipo_agent/nse.py`), fetches every source for one symbol with one API GET each, catches each source's failure into an `errors` list, and still returns the records of the sources that worked.
  - The **one deliberate probe** the roadmap allows: a single budget-capped run, written in the build (6a) and run once by the human after it, that tries the quote candidates in fixed order — the stock page's embedded quote JSON, the NextApi `_next/data` route found in that same page, `quote-equity?symbol=X&section=trade_info`, and plain `quote-equity?symbol=X` with the cookie-order prime — re-checks the consolidated endpoint once under the same run, records which candidate answered, saves a `quote.json` fixture when one does, and records the outcome in `data-sources.md` (6b).
  - Closing or recording the other 003 gaps in the same docs: EBITDA derived in code from stated fields with a documented formula; results unit (₹ lakh) recorded as the endpoint's unit with the response's own management-note-text evidence and a tested `to_crore` conversion in the parser; FII/DII recorded as reachable only through the XBRL filing (parsing out of scope here, flagged for 016); `promoter_pledged_pct` computed in code (`ROUND_HALF_UP` to 2 dp); pledge rows carrying the company name only.
  - Tests (`tests/test_stock_*.py`) against the saved `tests/fixtures/nse_stock/` fixtures only — no live sites, no AI APIs.
- **Out of scope:**
  - Writing any database row, table, migration or setting; anything in `web/`.
  - `EQUITY_L.csv` parsing and the stocks universe — that is 015. Name→symbol resolution for market-wide pledges is 015/018's job; the fetcher returns the company name as NSE gives it.
  - Downloading or parsing XBRL or PDF filings. FII/DII stay `None`; the XBRL link is kept as `source_url`. A later task (016/018) must add XBRL parsing before `fii_move`/`dii_move` alerts can fire; this plan only records the gap.
  - Change detection, alert rules (016), any AI call or `ai_*` column (020), the database driver or the Gemini client (018/020, part of D09's dependency half).
  - The GitHub Actions worker workflow (018) and any dispatch or schedule.
  - Touching `ipo_agent/nse_stock_smoke.py`: it stays the development probe that the smoke workflow runs and that owns the fixture provenance README. 014 may add the `quote.json` fixture entry next to it.
  - Editing protected paths: `analysis/`, `reports/`, `data/`, `ROUTINE.md`, `config/delivery.json`, `CLAUDE.md`, `.claude/`, `AGENTS.md`, `ROADMAP.md`.

## Approach

### 1. The package and the record shape (D09, decided)

D09 is decided (plan review, round 1): **a new top-level Python package `stock_worker/`**, standard-library only in this task, importing `ipo_agent.net.Client` for HTTP. It keeps `ipo_agent/` as the IPO routine untouched and leaves ADR-0002's stdlib rule intact (it binds `ipo_agent/` only). Later tasks bring the package's own dependencies through its own requirements file — the Postgres driver in 018, the Python Gemini SDK in 020 — each named in that task's plan. The app's Gemini module is TypeScript (`web/lib/`), so tech.md's "one module shared by the app and the worker" becomes one module per side; ADR-0026 (new, status **Proposed**) records both halves: the location and the dependency rule.

Every fetcher returns "plain records": dicts keyed **exactly as the `db.md` column names** — `revenue_cr`, `other_income_cr`, `expenses_cr`, `ebitda_cr`, `pat_cr`, `promoter_pledged_pct` and so on — with amounts already converted to the column's unit (₹ crore) inside the parser, percentages as `decimal.Decimal`, dates as ISO `YYYY-MM-DD` strings and timestamps as ISO 8601 strings with `+05:30` preserved from NSE's local times. Missing → `None`: a missing field is always `None`, never zero and never estimated; a stated `0` is a value. Fields that have no column (e.g. `period_start`, `audited`, the pledges' share counts and disclosure time, `isin`) stay in the record as extras, listed in the module docstring. Records hold `Decimal`, which stdlib `json` cannot serialise, so the dev CLI prints them with `default=str`. No fetcher writes to `data/`, `analysis/` or `reports/`; the only files this task's code writes are the probe's fixture in `tests/fixtures/nse_stock/` (and its manifest entry), because parse results only reach git-free files in 018.

### 3. Units, EBITDA, and the two "never infer" rules

- **Units.** The response states no unit field, but its own management-note text does, and that makes the unit a property of the **endpoint**, not of each fetch. RELIANCE's first `results_standalone.json` row has `re_net_sale` = `12826000` and `re_desc_note_seg` saying "Net Revenue is Rs 128,260 crore" — `12826000 lakh = 128260 crore`, so the results API's amounts are **₹ lakh**. `data-sources.md` records ₹ lakh as the endpoint's unit with this evidence; one test pins the evidence on the fixture; and `results.py` converts every amount to ₹ crore with the tested `to_crore` helper while building the records. There is no per-fetch regex gate on note text — few companies write a "Rs N crore" note, and 018 must not get `None`s where the unit is known. EPS (`re_basic_eps_for_cont_dic_opr`) is in ₹ per share and is **not** converted; a test pins that too.
- **EBITDA.** `results-comparision` has no EBITDA field. `results.py` derives **operating EBITDA, excluding other income**, only from fields that are stated: `ebitda_cr = revenue − (total expenses − finance costs − depreciation)`, from `re_net_sale`, `re_oth_tot_exp`, `re_int_new` and `re_depr_und_exp` (all ₹ lakh, before the `to_crore` conversion) — and only when all four are present; if any is absent, `ebitda_cr` is `None`. A stated `0` is a value, not a missing field. On the fixture's first row: 12,826,000 − (11,987,700 − 237,100 − 445,900) = 1,521,300 lakh → `Decimal("15213.00")` crore; the test pins it. The formula and the four field names are written in the module docstring, in `data-sources.md`, and as a one-line note under `ebitda_cr` in `db.md`; the derivation is a stated rule applied to stated fields, not a guess.
- **Consolidated results.** The `consolidated=true` endpoint returned a byte-identical body in 003; the probe re-checks it once (step 6b). Unless it answers with a distinct body, `results.py` returns no consolidated rows and the gap stays recorded. Standalone rows are never relabelled consolidated, and `consolidated` is always `False` for the comparison rows. The `data-sources.md` gap note records that the `Consolidated` *filings* rows carry an XBRL link — a likely consolidated source for a later task, not for this one.
- **FII/DII.** The shareholding JSON has no FII/DII split; the XBRL filing does. 014 does not fetch or parse XBRL; `fii_pct`/`dii_pct` are `None` and the gap is recorded for 016, whose `fii_move`/`dii_move` rules will need XBRL parsing (016's scope note; see "Doc updates").

### 4. Failure isolation and the "be gentle" budget

`stock_worker/fetchers.py` exposes one entry per source and `fetch_all(client, symbol, since=None)` that calls each source, catches each `FetchError`/`SourceError` into `errors = [{"source": ..., "error": ...}]`, and returns a bundle with the successful records — a failing source never stops the others, matching the "Rules for every source". The client is **primed once per run, not per source**: `ipo_agent/net.py`'s `Client` already primes its cookie jar once per client (`_primed`), and the fetchers reuse that pattern exactly as `ipo_agent/nse.py` does — so "one GET per source" means one API call per source plus one shared prime per run. The announcements fetcher with `since` still makes one GET; filtering is in code. The `fetch_all` test asserts the total call count (one prime + one API call per source) against a `FakeClient`. The probe run in steps 6a/6b is the only deliberate live request sequence in the task, and it is one run with a hard budget of 6 requests (1 prime + up to 4 candidate fetches + 1 consolidated re-check), stopping at the first working quote candidate; `CallBudget`-style guards and tests pin the count, exactly as in 003.

### 5. What is deliberately not here

The equity list (`EQUITY_L.csv`) parser is 015's; the smoke probe stays untouched; the worker's scheduling, database writes and AI calls are 016/018/020. This task ships code that is not yet called by any workflow — it is the calibrated, tested fetcher layer that 018 wires in.
